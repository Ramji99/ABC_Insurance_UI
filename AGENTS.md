## PROJECT OVERVIEW

ABC Health Claims Portal is a **multi-role, multi-view enterprise portal** for processing health insurance reimbursement claims. It handles the full lifecycle of a claim from inward entry through medico assessment, document upload, claim intimation, and payment. As of v2.0.0 the former single-page Inward Entry app has been **split into three standalone pages** (`index.html`, `process-claim.html`, `payment.html` — see Multi-Page Architecture below) that share small classic scripts under `shared/` (originally ES modules at the v2.0.0 split, converted to classic `<script>`-tag globals at v2.2.0 for `file://` compatibility — see Iterations v2.2.0), plus two further standalone dashboards (Email Pool, Email Team) — all sharing one design-token file and one shared header/component stylesheet.

## MULTI-PAGE ARCHITECTURE (index.html / process-claim.html / payment.html)

`index.html`, `process-claim.html`, and `payment.html` were originally a single SPA (`index.html` + `app.js`, everything as `.hidden`-toggled views on one page). They are now **three separate documents**, each with its own script entry point, that together implement the same role-driven workflow. This is the most important structural fact about this codebase — read it before touching navigation, role-switching, or any cross-page flow.

**Why it matters:** every top-level `let`/`const` in `shared/*.js` and each page's own script is reinitialized on every full page load (classic scripts, not ES modules — see File Structure). `shared/role-state.js`'s `currentRole` is the one exception, as of 2026-08-17: its top-level initializer now reads `?role=` from the URL itself (falling back to a `sessionStorage` key, `hcp_currentRole`, when no `?role=` is present), so the active role now survives a plain page refresh on `index.html`/`process-claim.html` — see "Role persistence" below. It still does **not** survive a navigation to a *different* page without an explicit `?role=` in the destination URL. Any state that must survive a cross-page navigation is passed via **URL query parameters**, not in-memory state.

**Query-param handoff pattern (the only supported way to carry state across these three pages):**
- `index.html` → `process-claim.html`: row-action "Process Claim" navigates to `process-claim.html?id=<inwardId>&role=<currentRole>`. `process-claim.js`'s `initFromQueryParam()` IIFE reads both params on load — `id` opens that claim's wizard via `openMedicoWizard(rec)`; `role` (if a valid `MEDICO_STAFF_ROLES` entry) restores the role via `setCurrentRole()` before rendering. Note this now partially overlaps with `shared/role-state.js`'s own automatic `?role=` restore (see below), which has already applied the same param by the time this IIFE runs — `initFromQueryParam()`'s own `setCurrentRole()` call is redundant in that case but still needed for its `MEDICO_STAFF_ROLES` validation and the `#profileRoleName` DOM sync, so it was left in place.
- `process-claim.html` → `index.html`: the wizard's Back button (`#backToListFromMedicoBtn`) calls `goToClaimsList()`, which navigates to `index.html?role=<currentRole>`. As of 2026-08-17, `app.js` no longer has its own restore IIFE for this — `shared/role-state.js`'s top-level initializer reads `?role=` (it runs before `app.js`, since it's loaded earlier in the `<script>` order — see File Structure) and applies it automatically; `app.js` just does a one-line `document.getElementById("profileRoleName").textContent = getCurrentRole();` sync near the end of its own top-level script, after the element exists, so the destination page reflects the role that was active on the page being left.

**Role persistence across refresh (added 2026-08-17):** `shared/role-state.js` no longer holds a plain `let currentRole = ROLES[0]`. It now has a `readRoleFromUrl()` helper (checks `?role=` first, then a `sessionStorage` fallback keyed `hcp_currentRole` for setups where the URL param isn't present) that seeds `currentRole` when the script first runs, and `setCurrentRole(role)` now also writes that `sessionStorage` key and calls `history.replaceState()` to keep the URL's `?role=` in sync with the in-memory role on **every** role change, not just during a cross-page navigation. Net effect: a plain refresh of `index.html` or `process-claim.html` now keeps whatever role was last selected instead of resetting to `ROLES[0]` ("Scan Tag"). `sessionStorage` is a best-effort fallback only — this app is opened as a local `file://` page, where `sessionStorage` is unreliable in some browsers (origin-isolated per file), so the URL query string is the primary persistence mechanism. `payment.html` is unaffected — it never loads `shared/role-state.js` and keeps fully local, non-shared role state (see Role System / Payment role notes).
- `process-claim.html`'s role-switch dropdown: switching role **always navigates away** — to `index.html?role=<role>` for any role (TL roles land on `index.html`'s TL Dashboard; staff roles land on the regular list), or to `payment.html` for the Payment role. It never re-renders the wizard in place and never shows a confirm dialog — every role has its own page/view to land on, so there is nothing to preserve across the switch.
- `index.html` → `payment.html`: role-switch to "Payment" navigates directly (`payment.html`, no query param needed — `payment.js` keeps its own independent local role state, since Payment has no cross-role data to preserve).

**Flash-of-wrong-role prevention:** `index.html`'s `<body>` starts with `class="role-init-pending"` (CSS: `body.role-init-pending { visibility: hidden; }`, defined inline in `<head>` since it must apply before any stylesheet-independent paint). `app.js` removes this class only after `updateRoleBasedListUI()` and the initial `renderTable()` have run — the correct role is now already resolved before this point, since `shared/role-state.js` (loaded earlier in the `<script>` order) restores it from `?role=`/`sessionStorage` as soon as it runs, ahead of any of `app.js`'s own top-level code — this still prevents the page from ever painting its hardcoded default ("Scan Tag") header/list before the real role is applied. `process-claim.html` and `payment.html` do not need this pattern since they have no equivalent hardcoded-default flash risk.

**Reference Panel document handoff:** the "Process Sheet" reference-panel link no longer embeds its target document as a JS template-literal string. `shared/process-sheet.html` (+ `shared/process-sheet.css`) is a real, independently-openable HTML file; `shared/process-sheet-loader.js`'s `getProcessSheetHTML()` fetches and caches it, and both `app.js` and `process-claim.js` `await` it before calling `showDocViewer()`. `process-sheet.html`'s own `<link>` tags use **root-absolute paths** (`/variables.css`, `/shared/process-sheet.css`) rather than relative ones — it is loaded three different ways (direct file open, injected via `docViewerFrame.srcdoc` where the base URL is the *host* page's, and via a `blob:` URL from "Open in new tab") and only a root-absolute path resolves correctly in all three. Do not change these back to relative paths.

**TL roles vs. staff roles:** `process-claim.html` shows the per-claim wizard for the roles in `process-claim.js`'s `MEDICO_STAFF_ROLES`, which currently is `["Medico", "Non Medico", "QC", "QC TL", "Payment Auditor - Settlement User"]` — **`QC TL` is included**, so unlike the other two TL roles it *can* reach the wizard page. `Medico TL` and `Non Medico TL` never see this page — they see `index.html`'s TL Dashboard (`#tlDashboard`, gated by `isTLRole` inside `updateRoleBasedListUI()`) instead. `index.html`'s row-action dispatcher only renders a "Process Claim" button for staff roles (plus QC TL), so the other two TL roles cannot normally reach `process-claim.html` — the `MEDICO_STAFF_ROLES` check in `process-claim.js` exists specifically to route around the in-wizard role-switch dropdown, which can attempt to switch to any role including a TL one.

### Searchable Select

Drop-in replacement UI for native `<select>` elements, styled and behaving like this app's Hospital Name autocomplete (`.autocomplete-wrap`/`.autocomplete-dropdown`/`.autocomplete-icon-trailing`). See Iterations v2.7.0 for the full design writeup.

```html

  <label for="myField">Field Label</label>
  <select id="myField">
    <option value="" selected disabled>--Select--</option>
    <option value="a">Option A</option>
  </select>
</div>
```
```js
initSearchableSelect("myField");              // static select, once
initSearchableSelectsIn(containerEl);          // bulk-wrap every <select> inside a container (dynamic grid rows, page load)
refreshSearchableSelectLabel("myField");       // call after any programmatic `select.value = ...` write
refreshAllSearchableSelects();                 // same, for a bulk filler that writes many selects at once
```
Leave the markup exactly as a plain `<select>` — `initSearchableSelect`/`initSearchableSelectsIn` inserts a `.searchable-select-wrap` (proxy text input + trailing search icon) immediately after it and visually hides the original (`.sr-only`, not `display:none`) as the source of truth for `.value`/`.disabled`/`change` listeners — every existing `document.getElementById(id).value`/`.disabled = ...`/`addEventListener("change", ...)` call site keeps working completely unchanged. `.disabled` is checked lazily on the proxy's own `focus`/`click`, not synced reactively. A true `multiple` `<select>` is out of scope (`initSearchableSelect` returns `null`) — see `stMedicoRemarksReason` in `process-claim.html`, already a custom checkbox-panel over a native multi-select using the same "keep the real control as source of truth" approach. The `.autocomplete-dropdown` option-list panel itself is NOT nested inside `.searchable-select-wrap` — it's appended to `<body>` and positioned with `position: fixed` (`.searchable-select-portal`), computed from the input's `getBoundingClientRect()` on every open/scroll/resize, same "portal" technique as `#rowMenu`/`.gs-dropdown__menu`. This matters for any select placed inside a `.table-scroll` (every repeating grid in this app) — a plain `position: absolute` panel nested in the wrap renders with zero visible pixels there, since `.table-scroll`'s `overflow-x: auto` clips the other axis too.

## FILE ORGANISATION RULES

These are non-negotiable per `AGENTS.md`.

| Rule | What This Means |
|---|---|
| No hardcoded colours | All colour, shadow, and radius values must use `var(--token)` from `variables.css`. Never write `#hex` or `rgba()` directly in `styles.css`. |
| No inline CSS | `style=""` is forbidden in `index.html`. Every presentation goes in `styles.css`. |
| No inline JS | `onclick=`, `onchange=` etc. are forbidden. Use `addEventListener()`. |
| No static HTML in JS | Don't build static UI in template literals. Static markup belongs in `index.html`. |
| JS = behaviour only | JS manages state, events, API calls, and dynamic DOM updates. |
| CSS = presentation only | CSS handles all visual appearance including states. |
| HTML = structure only | HTML provides semantic document structure. |

### When to add to each file

**`variables.css`** — Add here when:
- Adding a new brand colour, status colour, or palette scale token
- Adding a new shadow, radius, or layout dimension token
- Adding a new badge bg/text token pair
- A component needs a scoped token (prefix with component name, e.g. `--pc-`)
- Never add component-specific rules here — only raw values

**`index.html` / `process-claim.html` / `payment.html`** — Add markup to whichever page owns the affected view (see Application Architecture → Shell Layout for which page owns which view). Add here when:
- Creating a new view, section, card, form, modal, or panel
- Adding static placeholder content that JS will later populate
- Adding ARIA landmarks or semantic structure
- Do not duplicate markup that's identical across pages into each page's own file — extract it to a `shared/` script instead (see `shared/shared-components.js` for the existing pattern), *unless* the shared-extraction has already been tried and reverted for that specific piece (the Reference Panel — see Key Functions Reference → Shared Header and Iterations v2.0.0)

**`styles.css`** — Add here when:
- Styling anything new (component, state, utility, variant) that's used by two or more pages
- Converting an inline style violation to a class
- Adding responsive rules for new components
- Extend existing rules with a modifier class before creating new ones
- Page-specific styling only ever used by one page (Email Pool, Email Team) still belongs in that page's own `-styles.css`, not here

**`app.js` / `process-claim.js` / `payment.js`** — Add behaviour to whichever page owns the affected view. Add here when:
- Handling user interactions (always via `addEventListener`)
- Managing state changes
- Rendering dynamic content (use `createElement` / `classList` / `DocumentFragment`)
- Adding new view-switching logic (always call `hideAllViews()` first, on `index.html` — `process-claim.html`/`payment.html` have only one view each so there is nothing to hide)
- Logic used by more than one of these three pages belongs in a `shared/` script (loaded via `<script src>` before the page's own script, declared as plain globals — no `import`/`export`), not copy-pasted into each file — see Multi-Page Architecture and the existing `shared/` scripts

## HOW TO ADD A NEW VIEW

This assumes the new view belongs on `index.html` (the default — most views do, since it's the only one of the three multi-page-split pages with more than one view). If the feature is really a new standalone page in its own right, follow the pattern of `process-claim.html`/`payment.html` instead: its own `.html` + `.js` pair, classic `<script src>` tags (in the load order documented in File Structure) for whatever it needs from `shared/`, with a query-param handoff from `index.html` (see Multi-Page Architecture) rather than a `switchToXView()` function.

1. Add the HTML section in `index.html` inside `.main` as `<div id="viewMyFeature" class="hidden">...</div>`

5. Create `switchToMyFeatureView()` calling `hideAllViews()` first, then removing `.hidden` from the view and sidebar panel
6. Add CSS for the new view in `styles.css` — reuse existing tokens, utilities, and components
7. Wire navigation triggers via `addEventListener()`
